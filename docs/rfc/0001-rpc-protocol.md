本文档定义 ReactorNet RPC 层在 TCP 之上的**分帧格式**。它是 #27 的唯一实现依据：实现代码与本文档冲突时，以本文档为准（并提 PR 修正其中之一）。

本文档不含任何代码。它只规定「字节怎么摆」，不规定「字节怎么解释」——序列化方案是 #41 的事。

---

## 1. 摘要

RN RPC 帧 = **16 字节定长帧头** + **变长 body**。

- 帧头定长，字段位置永不变，多字节整数一律 **little-endian**。
- 分帧靠帧头尾部的 `body_len`（长度前缀），不靠任何分隔符——因为 TCP 上没有可靠的分隔符。
- `msg_type` 区分 REQUEST / RESPONSE；`request_id` 把两者配对。
- v0.1 的 payload 是**不透明字节**：协议层不解析，原样交给上层。这么做是为了把序列化决策推迟到 M5（#41），不阻塞网络层（M1）先落地。

---

## 2. 为什么先写这份文档

协议是整个 RPC 层里唯一「改起来最贵」的东西：一旦有第二个实现、有线上流量、有抓包存档，改一个字节偏移就要同时改客户端、服务端、测试向量、抓包分析工具。**在文档里改到满意，比在代码里改便宜一个数量级。**

本文档的验收标准不是「作者看懂了」，而是：**另一个人只看这份文档就能写出解码器，且写出来的与 #27 一致。**

---

## 3. 术语与约定

| 术语 | 含义 |
|---|---|
| 帧（frame） | 一次 RPC 交互在 TCP 上的完整字节序列：帧头 + body |
| 帧头（header） | 固定 16 字节，见 §4 |
| body | `body_len` 指定的变长部分 |
| payload | body 里除去协议字段后的、对协议层不透明的用户数据 |
| REQUEST | 客户端 → 服务端的帧（`msg_type = 1`） |
| RESPONSE | 服务端 → 客户端的帧（`msg_type = 2`） |
| 拒收（reject） | 判定对端违反协议，停止处理并按 §7 处理 |
| 容忍（tolerate） | 判定为「合法但本实现不认识」，必须忽略而非报错 |

约定：`MUST` / `MUST NOT` / `SHOULD` / `MAY` 按 RFC 2119 解释。

所有多字节整数字段**一律 little-endian**，包括 u16 与 u32；`magic` 是 2 个独立的 `u8`，与字节序无关。帧内**没有对齐填充**，任何字节都是有效载荷。

## 4. 线格式

### 4.1 总览

```
+---------------------- 16 字节固定帧头 ----------------------+------- body -------+
| magic | ver | type | flags | status | reserved | request_id | body_len |   body  |
|  2B   | 1B  |  1B  |  1B   |   1B   |    2B    |     4B     |    4B    | body_len|
+------------------------------------------------------------+----------+---------+
 0        2      3      4        5         6           8          12         16
```

### 4.2 帧头字段表

**「拒收」列的动作细节见 §7，status 取值见 §4.6。**

| 偏移 | 长度 | 字段 | 类型 | 取值域（合法值） | 发送方义务 | 接收方义务 |
|---|---|---|---|---|---|---|
| 0 | 2 | `magic` | 2× `u8` | 固定 `0x52 0x4E`（ASCII `"RN"`），**唯一合法值** | MUST 写 `52 4E` | 不等于 `52 4E` → **立即关闭连接**，不回响应、不做重同步 |
| 2 | 1 | `version` | `u8` | v0.1 为 `0x01`；`0x00` 及 `0x02`–`0xFF` 对 v0.1 实现均为未知 | MUST 写 `0x01` | 未知 → 回 `UNSUPPORTED_VERSION` 后关闭 |
| 3 | 1 | `msg_type` | `u8` | `1` = REQUEST，`2` = RESPONSE；其余值保留 | MUST 写 `1` 或 `2` | 未知 → 回 `UNSUPPORTED_MSG_TYPE` 后关闭 |
| 4 | 1 | `flags` | 位域 `u8` | 见 §4.5 | v0.1 MUST 写 `0x00` | 未定义位 MUST 忽略；已定义未实现位 → 拒收（`UNSUPPORTED_FLAG`） |
| 5 | 1 | `status` | `u8` | 见 §4.6。RESPONSE：`0x00`–`0xFF`；REQUEST：**只能为 `0x00`** | REQUEST MUST 写 `0x00`；RESPONSE 填结果码 | REQUEST 中非 `0` → 拒收。RESPONSE 中未知值 → 按「失败」容忍（§8） |
| 6 | 2 | `reserved` | 2× `u8` | 发送：只能 `00 00`；接收：任意值均忽略 | MUST 写 `00 00` | MUST 忽略其值，**MUST NOT 复用为业务字段**（§9） |
| 8 | 4 | `request_id` | `u32` LE | `1` – `0xFFFFFFFF`；**`0` 非法** | 客户端分配；RESPONSE MUST 回显请求里的值 | `0` → 回 `BAD_REQUEST_ID` 后关闭 |
| 12 | 4 | `body_len` | `u32` LE | `0` – 本实现上限（见 §4.4） | MUST 等于实际 body 字节数 | 超本实现上限 → 拒收（`BODY_TOO_LARGE`）；**MUST NOT 按声明长度分配内存** |
| 16 | 变长 | `body` | 字节序列 | 见 §4.3 | —— | 长度必须恰好等于 `body_len` |

**字段位置永不变**：即使 `version` 不认识，16 字节帧头的布局仍然成立——这是 v0.1 实现能读出 `request_id` 并回一个带配对的 `UNSUPPORTED_VERSION` 响应的前提。详见 §9。

### 4.3 body 布局

#### REQUEST

```
偏移（相对 body 起点）   长度            字段
0                        2               svc_len      (u16 LE)
2                        svc_len         service      (UTF-8，不带 NUL 结尾)
2 + svc_len              2               method_len   (u16 LE)
4 + svc_len              method_len      method       (UTF-8，不带 NUL 结尾)
4 + svc_len + method_len 剩余             payload      (不透明字节，可为 0 字节)
```

约束（违反任一条 → 拒收，`MALFORMED_BODY`）：

- `svc_len >= 1` 且 `method_len >= 1`——空服务名/方法名没有意义，属于发送方 bug。
- `2 + svc_len` 不得越过 body 末尾。
- `4 + svc_len + method_len` 不得越过 body 末尾。
- 解析必须**恰好消费 `body_len` 字节**：`payload_len = body_len - (4 + svc_len + method_len)`，且 `payload_len >= 0`。

> 长度前缀不设单独上限（比如「服务名不得超 255 字节」）：`body_len` 已经有实现上限，长度前缀又必须落在 body 内，两者已经封顶了最坏情况。多定一个数字只会制造一个跨实现的兼容陷阱。

`service` / `method` 是**标识符**，不是路径：不含 `/`、不含 NUL。

#### RESPONSE

```
偏移（相对 body 起点）   长度            字段
0                        剩余全部         payload
```

`status` 在帧头（不在 body）。body 的含义完全由帧头的 `status` 决定：

- `status == 0x00 (OK)`：payload 是响应数据。
- `status != 0x00`：payload 是**错误描述文本**（UTF-8，允许 0 字节）。它是给人看的诊断信息，不是给程序解析的结构——程序只看帧头的 `status`。

**v0.1 的 payload 对协议层不透明。** 协议层不关心它是 JSON、protobuf 还是随手拼的字节；序列化方案推迟到 #41（M5）决定。这意味着本文档不定义「响应数据长什么样」，只定义「响应数据装在哪」。

### 4.4 `body_len` 上限

- 协议要求：**任何实现 MUST 能接收 body 至少 64 KiB（65536 字节）的帧**。这是互通底线。
- 实现 MAY 设置更高的上限。参考实现（#27）建议取值 **16 MiB（16777216）**，作为编译期常量 `kMaxBodyLen`。
- 收到的 `body_len` 超过**本实现**上限 → 回 `BODY_TOO_LARGE`（若 `request_id` 已可读出）后关闭连接。
- **铁律：校验先于分配。** 解码器必须先读满 16 字节帧头、校验 `magic` / `version` / `body_len` 上限，**然后**才允许为 body 预留内存。`body_len` 是攻击者可控的 `u32`——看到 `0xFFFFFFFF` 就 `new char[len]` 的实现会直接被一行流量打爆（`bad_alloc` 或 OOM）。

### 4.5 `flags` 位定义

| 位 | 名称 | v0.1 发送 | v0.1 接收 |
|---|---|---|---|
| bit0 | `COMPRESSED` | MUST `0` | 置位 → 拒收（`UNSUPPORTED_FLAG`） |
| bit1 | `ONEWAY` | MUST `0` | 置位 → 拒收（`UNSUPPORTED_FLAG`） |
| bit2–bit7 | 未定义（保留） | MUST `0` | **MUST 忽略**，不得报错 |

区分「未定义位」与「已定义但未实现的位」是刻意的：

- **未定义位**（bit2–7）旧实现无法知道它意味着什么，按 Postel 定律忽略是安全的——它只能来自「更新的对端在做一个旧端不关心的优化」。
- **已定义但未实现位**（bit0 压缩、bit1 oneway）忽略是**不安全**的：把压缩过的字节当 payload 交给上层，是静默的数据损坏；把 oneway 请求当普通请求处理，会发出对端不期待的响应。既然不能安全地忽略、也不能安全地实现，v0.1 唯一安全的动作就是停下来。

> 说明：此处相对 issue #15 的描述做了一处收紧。issue 写「接收时必须忽略未知位」——本文档保留这条（针对未定义位），并补充「已定义未实现位必须拒收」，理由是前述的静默损坏风险。

`ONEWAY` 被拒收看似矛盾（拒收时我们还要发一个响应，而对端说自己不等响应）。但这恰恰是它必须被拒收的原因：v0.1 既不能正确地服务它，也不能安全地丢弃它，只能终止连接让上层重连或降级。

### 4.6 `status` 状态码

| 值 | 名称 | 方向 | 含义 | 回响应后是否关闭连接 |
|---|---|---|---|---|
| `0x00` | `OK` | S→C | 成功，body 是响应数据 | 否 |
| `0x01` | `UNSUPPORTED_VERSION` | S→C | `version` 不认识（payload 可含诊断文本） | **是** |
| `0x02` | `UNSUPPORTED_MSG_TYPE` | S→C | `msg_type` 不认识 | **是** |
| `0x03` | `UNSUPPORTED_FLAG` | S→C | `flags` 含已定义但 v0.1 未实现的位 | **是** |
| `0x04` | `BAD_REQUEST_ID` | S→C | `request_id == 0` | **是** |
| `0x05` | `BODY_TOO_LARGE` | S→C | `body_len` 超本实现上限 | **是** |
| `0x06` | `MALFORMED_BODY` | S→C | body 的长度前缀越界，或 `svc_len` / `method_len` 为 0 | **是** |
| `0x07` | `UNKNOWN_SERVICE` | S→C | 服务未注册（M2 起使用） | 否 |
| `0x08` | `UNKNOWN_METHOD` | S→C | 方法未注册（M2 起使用） | 否 |
| `0x09` | `INTERNAL_ERROR` | S→C | 服务端内部错误（业务异常） | 否 |
| `0x0A`–`0x7F` | 保留 | —— | v0.1 未定义；收到按「失败」容忍（§8） | —— |
| `0x80`–`0xFF` | 应用自定义 | S→C | 留给上层定义；v0.1 协议层不产生 | 否 |

**`0x01`–`0x06` 是协议级错误：回响应后立即关闭连接。** `0x07`–`0x09` 是应用级错误：body 分帧完好、连接状态未被污染，连接可以继续复用。

注意 `magic` 不匹配**没有**对应的状态码——它是唯一一个「连响应都不回就关连接」的错误。理由：`magic` 错了说明对面可能根本不是 RN 协议（可能是 HTTP、是端口扫到了别的服务、是二进制垃圾），给一个非 RN 对端回一段 RN 帧毫无意义，反而可能被当成别的协议的合法输入。

## 5. Golden 向量

以下十六进制样例是**规范性的**：任何实现都必须能用它们做 round-trip 测试（编码得到这些字节、解码这些字节得到同样的字段）。所有向量均由 §5.4 的脚本生成而非手敲。

### 5.1 `GetUser` REQUEST（47 字节）

```
0000  52 4e 01 01 00 00 00 00  01 00 00 00 1f 00 00 00   RN..............
0010  0b 00 55 73 65 72 53 65  72 76 69 63 65 07 00 47   ..UserService..G
0020  65 74 55 73 65 72 7b 22  69 64 22 3a 34 32 7d        etUser{"id":42}
```

逐字节核对：

| 偏移 | 字节 | 字段 | 解读 |
|---|---|---|---|
| 0–1 | `52 4e` | `magic` | ASCII `"RN"` |
| 2 | `01` | `version` | 1 |
| 3 | `01` | `msg_type` | 1 = REQUEST |
| 4 | `00` | `flags` | 无标志位 |
| 5 | `00` | `status` | REQUEST 必须为 0 |
| 6–7 | `00 00` | `reserved` | 保留，必须为 0 |
| 8–11 | `01 00 00 00` | `request_id` | 1（LE） |
| 12–15 | `1f 00 00 00` | `body_len` | **31**（LE）= 0x1f |
| 16–17 | `0b 00` | `svc_len` | 11 |
| 18–28 | `55 73 ... 63 65` | `service` | `"UserService"`，11 字节 |
| 29–30 | `07 00` | `method_len` | 7 |
| 31–37 | `47 65 74 55 73 65 72` | `method` | `"GetUser"`，7 字节 |
| 38–46 | `7b 22 ... 34 32 7d` | `payload` | `{"id":42}`，9 字节 |

自洽性验算：

```
帧头            16
svc_len 字段     2
service         11
method_len 字段  2
method           7
payload          9
------------------------------
body  = 2 + 11 + 2 + 7 + 9 = 31   ← 与偏移 12 的 body_len 字段一致 ✓
总计  = 16 + 31            = 47   ← 与 hexdump 实际字节数一致 ✓
```

`payload` 内容 `{"id":42}` 只是**测试夹具**：v0.1 的 payload 不透明，把它换成任意 9 字节，帧的合法性不变（只有 `body_len` 必须跟着变）。

### 5.2 RESPONSE / `OK`（40 字节）

`request_id = 1` 的成功响应，payload = `{"id":42,"name":"alice"}`（24 字节）。

```
0000  52 4e 01 02 00 00 00 00  01 00 00 00 18 00 00 00   RN..............
0010  7b 22 69 64 22 3a 34 32  2c 22 6e 61 6d 65 22 3a   {"id":42,"name":
0020  22 61 6c 69 63 65 22 7d                            "alice"}
```

`msg_type = 02`（RESPONSE）、`status = 00`（OK）、`request_id` 回显为 `01 00 00 00`、`body_len = 0x18 = 24`，16 + 24 = 40 ✓

### 5.3 RESPONSE / `UNSUPPORTED_VERSION`（41 字节）

`request_id = 7` 的错误响应，payload 为错误描述文本 `unsupported version: 0x02`（25 字节）。

```
0000  52 4e 01 02 00 01 00 00  07 00 00 00 19 00 00 00   RN..............
0010  75 6e 73 75 70 70 6f 72  74 65 64 20 76 65 72 73   unsupported vers
0020  69 6f 6e 3a 20 30 78 30  32                        ion: 0x02
```

`status = 01`（`UNSUPPORTED_VERSION`）、`body_len = 0x19 = 25`，16 + 25 = 41 ✓。这一帧发完即关闭连接（§4.6）。

### 5.4 如何复现这些向量

```python
import struct

def frame(msg_type, flags, status, rid, body):
    if isinstance(body, str):
        body = body.encode()
    h = struct.pack('<2sBBBBHII', b'RN', 1, msg_type, flags, status, 0, rid, len(body))
    assert len(h) == 16
    return h + body

def req_body(svc, method, payload):
    return (struct.pack('<H', len(svc)) + svc.encode()
            + struct.pack('<H', len(method)) + method.encode() + payload.encode())

print(frame(1, 0, 0x00, 1, req_body('UserService', 'GetUser', '{"id":42}')).hex(' '))
print(frame(2, 0, 0x00, 1, '{"id":42,"name":"alice"}').hex(' '))
print(frame(2, 0, 0x01, 7, 'unsupported version: 0x02').hex(' '))
```

`struct` 的 `<` 前缀就是 little-endian 且无对齐——它和本文档的字节布局是同一个语义（这也是 §10 里反对 `memcpy` 结构体的实证：`<` 是显式声明的，C++ 编译器默认给的既不是 `<` 也不保证稳定）。

## 6. 解码流程（粘包 / 半包）

**TCP 是字节流，不是消息流。** 它不保留任何「写」的边界：对端一次 `write` 47 字节，你这边的 `read` 可能只拿到 12 字节（半包），也可能一次拿到两个半帧（粘包）。所以分帧必须由协议自己做——这也是 `body_len` 存在的全部意义。

解码器必须是「缓冲 + 状态机」，不能假设「一次 `read` 一帧」：

```
WAIT_HEADER ──readable >= 16──► 校验帧头 ──通过──► WAIT_BODY ──readable >= body_len──► 派发 ──► 回到 WAIT_HEADER
     ▲                              │                                                       │
     └────────── 数据不够，继续收 ───┘                              retrieve 掉已消费字节 ◄──┘
```

要点：

1. **帧头必须一次凑齐再解析。** `readableBytes() < 16` 时不得尝试解析任何字段——哪怕是偏移 0 的 `magic`。
2. **body 未收全不得派发**，也不得因为 `body_len` 大就先把缓冲区撑到那个大小；上限校验（§4.4）必须在这一步之前完成。
3. **一个缓冲区里可能同时存在多个完整帧和一个半帧**。必须循环解码直到剩余不足一帧，再回到事件循环等下一批数据。
4. **不要按单次 `read` 的边界对齐业务语义。** 一次读到的「一个完整帧」是巧合，不是契约。
5. 派发后立刻 `retrieve` 掉已消费的字节，否则缓冲会无限增长。

对 #27 的具体约束：解码器跑在现有 `Buffer`（`readableBytes()` / `peek()` / `retrieve()`）之上，不得依赖单次 `read` 的返回边界，也不得假设 `Buffer` 底层是连续内存（它只在可读区连续，内部会搬移/扩容）。

## 7. 拒收清单（MUST reject）

| # | 触发条件 | 动作 | 理由 |
|---|---|---|---|
| 1 | `magic != 52 4E` | **立即关闭连接**，不回响应，**不做重同步** | 对面可能根本不是 RN 协议。试图在字节流里「找下一个 `RN`」会把二进制垃圾误判成帧，还会被构造出来的假 magic 牵着走 |
| 2 | `body_len > 本实现上限` | 回 `BODY_TOO_LARGE`（若 `request_id` 可读）后关闭；**MUST NOT 按声明长度分配内存** | 声明长度是攻击者可控输入。先分配后校验 = 一行流量打爆进程（§4.4） |
| 3 | `version` 不认识 | 回 `UNSUPPORTED_VERSION` 后关闭 | 语义未知，继续解析等于猜 |
| 4 | `msg_type` 不认识 | 回 `UNSUPPORTED_MSG_TYPE` 后关闭 | 不静默丢弃：对端可能在等一个响应，丢弃会造成悬挂直到超时；而响应方向本身也未知，只能终止 |
| 5 | `request_id == 0` | 回 `BAD_REQUEST_ID` 后关闭 | `0` 是「未初始化」的哨兵值（`memset` 出来的默认值）。允许它会把「忘了填」变成一个合法请求 |
| 6 | REQUEST 的 `status != 0` | 拒收，回 `MALFORMED_BODY` 后关闭 | 任何合法版本的发送方都不会这么写。这不是前向兼容问题，是发送方 bug |
| 7 | body 长度前缀越界，或 `svc_len` / `method_len == 0` | 回 `MALFORMED_BODY` 后关闭 | 长度前缀越界是经典的解析漏洞入口（读越界 / 死循环） |
| 8 | 方向不符（client 收到 REQUEST，或 server 收到 RESPONSE） | 拒收后关闭 | 角色是连接建立时就确定的。允许反向帧会让「谁是客户端」变成运行时猜测 |
| 9 | `flags` 的 bit0 / bit1 置位 | 回 `UNSUPPORTED_FLAG` 后关闭 | 不能安全忽略、也不能安全实现（§4.5） |

---

## 8. 容忍清单（MUST tolerate）

Postel 定律：**发送时严格，接收时宽容。** 但宽容只给「扩展位」，不给「语义位」——`magic`、`version`、长度前缀一律严格，因为对它们宽容就是静默误解。

| # | 情况 | 必须怎么做 |
|---|---|---|
| 1 | `flags` 的 bit2–bit7 置位 | **忽略**，正常处理。它们只能来自更新的对端，且旧实现对它们无所求 |
| 2 | `reserved` 非 `0` | **忽略其值**，正常处理（发送时仍必须写 `00 00`） |
| 3 | RESPONSE 的 `status` 是未定义值（`0x0A`–`0x7F`） | 一律按**失败**处理，payload 当错误文本；不得崩溃、不得当成 `OK` |
| 4 | RESPONSE 的 `status != OK` 且 payload 为空 | 合法。错误文本允许为空，不得因此崩溃 |
| 5 | payload 比「预期」长 | 协议层不做任何校验——v0.1 的 payload 不透明，长度语义属于应用层（#41） |
| 6 | 一帧之后紧跟下一帧 | 正常现象（粘包），不是协议错误 |
| 7 | RESPONSE 的 `request_id` 本地没有对应请求 | 协议层视为合法帧并交给上层；上层丢弃（可能是超时后的迟到响应） |

**宽容的代价**要写清楚：上面每一条都在用「放弃检测一个错误」换「兼容一个未来版本」。所以这张清单必须短、必须显式、必须只覆盖「忽略它是安全的」那些位。任何「忽略它可能造成数据损坏」的情况（比如压缩标志）都不进这张清单，而进 §7 的拒收清单。

## 9. 兼容性与版本演进

### 9.1 永久冻结（不可回退的承诺）

1. **帧头布局冻结**：16 字节，偏移 0–15 的字段划分、长度、字节序永不变。
   理由：`version` 未知时仍要能读出 `request_id`。读不出 `request_id`，就回不了一个配对的 `UNSUPPORTED_VERSION`，对端只能靠超时才发现版本不兼容——那是最糟的失败模式。
2. **`magic` 冻结**：`"RN"` 永不改变。要换协议就换 magic 起一个新协议，不复用这个名字。
3. **已发布版本的语义不改**：`0x01` 永远是本文档定义的东西。发现 v0.1 有设计缺陷？提 `0x02`，不要偷偷改 `0x01`——已经部署的实现不会知道。

### 9.2 `version` 何时递增

只在**语义不兼容**时递增。下面这些**不算** breaking，因此**不**递增：

- 新增一个 `flags` 位（旧实现忽略它——§8 第 1 条）。
- 服务端新增一个 `service` / `method`（旧客户端根本不会调它）。
- payload 的序列化格式演进（对协议层不透明；但**对应用层是 breaking**，那是 #41 要处理的事，不是 `version` 的事）。

需要递增的情况：`msg_type` 增加新值、帧头字段语义变化、长度前缀规则变化、body 布局规则变化。

### 9.3 扩展点与纪律

| 扩展点 | 怎么用 | 纪律 |
|---|---|---|
| `flags` 新位 | **首选**的无痛扩展方式。只有置位才生效，旧实现忽略 | 新位的语义必须是「可安全忽略」的。做不到就说明它不该放在 `flags` 里 |
| `reserved` 2 字节 | 留给「必须在帧头里、且旧实现必须能安全跳过」的字段 | **MUST NOT 当作普通字段复用**。旧实现会忽略它，语义分歧会**静默**发生——不是失败，是两边理解不一致，这类 bug 最难查。要用它，必须先证明「忽略它是安全的」 |
| `msg_type` 新值 | 属于 breaking（旧实现按 `UNSUPPORTED_MSG_TYPE` 关闭） | 必须配 `version` 递增 |
| body 追加字段 | 只能追加在 payload **之后**（不能插入 `svc_len` 之前打断前缀结构） | 协议层能安全跳过，但应用层可能把新字段当成 payload 的一部分而误解 → 语义变化仍需递增 `version` |

### 9.4 演进策略：没有协商，只有明确失败

v0.1 **不做**版本协商、不做能力位、不做降级协商（协商机制本身需要协议支持，属于先有鸡还是先有蛋的问题）。

替代方案是「明确失败」：v0.1 实现遇到不认识的 `version` 会**回一个 `UNSUPPORTED_VERSION` 然后关闭**（§4.6）。这条规则的价值在于——当 `0x02` 上线时，旧的 v0.1 实现会**明确报错**，而不是静默误解。协议演进里最贵的从来不是「不兼容」，是「不兼容但没人发现」。

多版本协商留给以后（需要时提新 RFC，且必须能作为 `flags` 位或新 `msg_type` 在不破坏 v0.1 的前提下引入）。

## 10. 设计取舍

**为什么 `status` 放帧头而不是 body？**
出错时客户端不必解析 body 就能知道结果。更关键的是避免递归困境：如果「错误响应」的解析规则藏在 body 里，那么「解析错误响应的代码」本身也可能失败，而它失败时没有更低一层可以用来报告。

**为什么 `service` / `method` 放 body 而不是帧头？**
帧头必须定长，服务名是变长的。放 body 的代价是每帧多一次长度前缀解析；收益是帧头永远只有 16 字节、永远可以「先读 16 字节再决定」——这是整个解码状态机能成立的基础。

**为什么绝不 `memcpy` 结构体上 wire？**
填充、对齐、ABI、字节序，四项全部不可控：

- 编译器可以在成员之间插入填充字节（`struct { uint8_t a; uint32_t b; }` 在 x86-64 上 `sizeof` 通常是 8 而不是 5），且填充内容未定义——直接 `memcpy` 会把未初始化内存发到网络上（信息泄漏）。
- 取消填充要靠 `#pragma pack` / `__attribute__((packed))`，那是编译器扩展，不是标准 C++。
- 字节序取决于机器，大端机上发出去的 `body_len` 是反的。
- C++ 标准不规定结构体布局，换个编译器/优化级别就可能变。

所以：**手动逐字节写**，并用 `static_assert(kHeaderSize == 16)` 把「帧头是 16 字节」钉死在编译期。`static_assert` 是免费的对拍——任何改动破坏了帧长，编译就不过。

**为什么长度前缀协议必须先校验再分配？**
`body_len` 是攻击者可控的 `u32`。声明长度**不是可信输入**，它只是对端的一句话。先 `new char[body_len]` 再校验的实现，收到 `0xFFFFFFFF` 就会申请 4 GiB。顺序必须是：读满帧头 → 校验 `magic`/`version`/`body_len` 上限 → 才决定分配和等待。

**为什么 `request_id == 0` 非法？**
`0` 是所有「未初始化」的默认值（`memset`、零初始化的结构体）。把它定为非法，可以让「忘了填 `request_id`」在测试里立刻暴露，而不是变成一个能和响应配对的合法请求、把 bug 推迟到线上。

**为什么帧头定长 16 字节，而不是 TLV / 变长头？**
定长头让「读够 16 字节就能算出整帧还要多少字节」成立——这是长度前缀分帧的前提。变长头意味着你得先解析才能知道头有多长，分帧和解码就纠缠在一起了。另外定长头让 `version` 未知时仍能定位 `request_id`（§9.1）。

**粘包 / 半包的本质？**
TCP 是字节流，不是消息流。它只保证字节顺序，不保证任何「写入边界」——四次 `write` 可能被一次 `read` 拿到，一次 `write` 也可能被拆成多次 `read`。所以**分帧是应用层协议的责任**，长度前缀是其中最便宜的一种做法（对比：分隔符要处理转义，定长帧浪费带宽）。§6 的状态机就是这件事的实现形态。

## 11. 非目标（Non-Goals）

本文档**不**设计、**不**预留实现细节：

- 压缩（`flags` bit0 只为占位，v0.1 拒收）
- 流式 / 分块传输
- 鉴权、加密、TLS
- 多路复用并发窗口与流控（`request_id` 天然支持请求配对，但 v0.1 不定义「同时在途多少请求」的语义）
- 序列化方案（#41 / M5）
- 超时、重传、连接池、服务发现
- 背压与写缓冲上限
